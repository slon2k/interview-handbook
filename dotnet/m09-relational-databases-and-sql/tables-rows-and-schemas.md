# Tables, Rows, and Schemas

## Definition

A relational database organizes data into **tables** (relations), each with a fixed set of typed **columns** and any number of **rows**, where each row represents one record conforming to that structure. A **schema** is both the overall structure of a database (its tables, columns, and relationships) and, in most SQL dialects, a namespace for grouping related tables (e.g., `sales.Orders` vs. `hr.Employees`).

```sql
CREATE TABLE Orders (
    Id INT PRIMARY KEY IDENTITY,
    CustomerId INT NOT NULL,
    OrderDate DATETIME2 NOT NULL,
    Total DECIMAL(10,2) NOT NULL
);
```

## Alternatives & Trade-offs

A fixed, typed schema catches structural errors at write time (a string can't be inserted into an `INT` column) and lets the database enforce consistency across every row uniformly. This is the core trade-off relational databases make against schema-less/document stores: strong upfront structure and consistency guarantees, at the cost of needing a migration to change that structure later rather than each record being free to have its own shape.

## How It Works

### Column types constrain what a row can store

```sql
CREATE TABLE Products (
    Id INT PRIMARY KEY IDENTITY,
    Name NVARCHAR(200) NOT NULL,
    Price DECIMAL(10,2) NOT NULL,
    CreatedAt DATETIME2 NOT NULL DEFAULT SYSUTCDATETIME()
);
```

Every row in `Products` has exactly these four columns with these types — there's no way to insert a row missing `Price` or with `Price` as text, short of the database rejecting the statement.

### Schemas as namespaces

```sql
CREATE SCHEMA sales;
CREATE TABLE sales.Orders (Id INT PRIMARY KEY, ...);

CREATE SCHEMA hr;
CREATE TABLE hr.Employees (Id INT PRIMARY KEY, ...);

SELECT * FROM sales.Orders; -- fully qualified name avoids ambiguity and groups related tables
```

Schemas let a large database organize tables by domain/module and apply permissions at the schema level (e.g., the `hr` schema readable only by HR-related application roles).

### A row is a single, complete record

```sql
INSERT INTO Orders (CustomerId, OrderDate, Total) VALUES (7, '2026-08-25', 149.99);
-- this row now exists with all four columns populated (Id auto-generated by IDENTITY)
```

## Application

Design tables so each represents one clear concept (an `Order`, a `Customer`), with column types that match the actual data (don't store a date as a string, don't store money as a floating-point type — use `DECIMAL`/`NUMERIC` for money to avoid floating-point rounding errors). Use schemas to group related tables in larger databases and to apply access control at a coarser grain than individual tables.

## Common Mistakes

- Storing money as `FLOAT`/`DOUBLE` instead of `DECIMAL`/`NUMERIC`, introducing floating-point rounding errors into financial calculations.
- Using an overly generic column type (`NVARCHAR(MAX)` for everything) instead of types that constrain and document intent (dates as `DATETIME2`, small enumerations as a constrained type).
- Treating "schema" ambiguously in conversation — confusing "the overall database structure" with "a specific namespace" can cause real miscommunication in a design discussion.
- Not using `NOT NULL` where a value is always logically required, silently allowing incomplete data that then needs to be handled everywhere the column is read.

## Common Interview Questions

### Basic
- What is the difference between a table, a row, and a column?
- What are the two meanings of "schema" in a SQL context?

### Intermediate
- Why should money be stored as `DECIMAL` rather than a floating-point type?
- What's the benefit of grouping tables into schemas/namespaces in a large database?

### Advanced
- How would you design table structure and schema organization for a system with clearly separated business domains (sales, HR, inventory)?
- What are the trade-offs of a fixed relational schema compared to a schema-less document store for a given data shape?

### Follow-up Questions
- Can column types be changed after a table already contains data?
- Does every SQL database support the schema-as-namespace concept the same way?

### Code Prediction
Given `Price DECIMAL(10,2)` and an attempt to insert `Price = 19.999`, what happens — is it rejected, rounded, or truncated? Why does this matter for financial correctness compared to a floating-point column silently losing precision differently?

## Practical Tasks

- Design a table schema for an e-commerce domain (products, orders, customers) with appropriate column types.
- Organize a set of related tables into schemas by business domain and demonstrate qualified references.
- Identify and fix a column using an inappropriate type (e.g., money as `FLOAT`, a date as `VARCHAR`) in a given schema.

## Readiness Criteria

Design a table structure with appropriate column types and constraints, and use schemas to organize a larger database logically.
